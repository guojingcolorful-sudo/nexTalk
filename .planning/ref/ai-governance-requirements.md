# AI 输出治理需求文档（NexTalk）

> 需求来源：用户 2026-09-29 两轮系统设计论述（系统论要素-连接-功能框架；三层容错架构）+ 失败案例库与回归评测补充。
> 本文档是 AI 输出治理的**需求口径**——用户视角的期望与验收标准；实现决策见 `02-CONTEXT.md`（D-01..D-20）与 `02-AI-SPEC.md`。
> 需求编号 GOV-xx 供跨阶段追溯；与 REQUIREMENTS.md 的 UI-/SYNC-/AUDI- 体系并行。

## 0. 背景与目标

NexTalk 的实时语音翻译链以云端 LLM 为内核。LLM 输出具有内在不确定性；产品的竞争力不在于模型多强，而在于**系统设计是否让 AI 输出可控、可溯源、可观测、可兜底、成本可算**——用系统论的方法，把 LLM 的不确定性关进工程化的笼子里。

系统论映射（用户手绘框架的工程落位）：

| 系统论层级 | NexTalk 模块 | 治理原则 |
|-----------|-------------|---------|
| 外部输入 | 音频流、多语言、设备、网络 | 鲁棒性（输入质量不稳定时的兜底） |
| 要素 | ASR 转写、LLM 翻译、术语库、用户上下文 | 可控（置信与弃权） |
| 连接 | 管线：音频→转写→翻译→输出 | 可兜底（重试/熔断/降级） |
| 输出与反馈 | 译文展示、低置信标记、错误反馈 | 可观测 + 可溯源 |
| 循环/闭环 | 失败案例库 → 修复 → 回归评测 | 越用越准，而非每次从零开始 |

## 1. 总原则

1. **可控**：宁可让用户看到「这句没翻译好」，也不让用户看到一句「看起来流畅但完全错误的译文」。
2. **可溯源**：每一句译文都能追溯到音频时间戳、术语库来源、模型与版本。
3. **可观测**：每个模块的状态、置信度、成本都有埋点；观测是控制的前提，看不见就管不住。
4. **可兜底**：用户永远不会看到卡死或空白，系统不会因单点故障雪崩。
5. **成本可算**：先归因（哪一阶段在烧钱），再限额，最后优化。
6. **反馈闭环**：每一只逃出来的 bug 都要变成笼子上的新栅栏（失败案例库 → 回归评测）。

## 2. 三层容错架构

| 层 | 负责 | 落位 |
|----|------|------|
| 前端层 | UX 兜底：输入校验（麦克风权限/网络）、状态展示（正在转写/翻译/失败）、低置信标记、重试按钮、本地缓存 | 手机 H5 / 桌面 Webview（Phase 1 已建基础，Phase 2 扩展状态与标记） |
| 网关层 | 请求路由、重试、熔断、降级、成本闸门、模型切换 | **桌面 Rust 内核**（Phase 2 落地 D-09..D-15）；远程网关（服务器持 key）随商业化引入（Phase 8） |
| 管理后台 | 观测、配置、复盘、人工干预：成本看板、错误日志、卡点分析、模型切换开关、配额管理、人工确认 | Phase 8（公测前） |

卡点三分类：前端卡点（权限/网络/输入质量→提示+重试）；后端卡点（超时/限流/模型故障/成本超限→重试/熔断/降级/拒绝）；管理后台卡点（发现哪个环节失败率高、哪个用户烧钱多、哪个模型差→观测与配置）。

## 3. 需求明细

### 3.1 可控

- **GOV-01 三因子置信**：作为用户，我希望系统对每句译文的把握程度被量化，以便我知道何时该怀疑。验收：置信度 = STT 置信 × 翻译置信 × 术语命中率三因子加权；阈值与权重经实验数据标定。依据 D-01。阶段：Phase 2。
- **GOV-02 低置信标记**：作为用户，我希望低置信译文有明显红色标记，而中置信不在直播中打扰我。验收：仅低置信气泡角红色「低置信」微章；中置信黄色提醒只在复盘报告。依据 D-02。阶段：Phase 2（实时标记）+ Phase 6（复盘黄标）。
- **GOV-03 无声弃权**：作为用户，我希望音频无有效内容时系统诚实标记「待翻译」，而非硬编。验收：abstained 事件 + 「待翻译」标记；低置信不弃权（实时面试必须连续输出）。依据 D-03。阶段：Phase 2。
- **GOV-04 输出前确定性校验**：作为用户，我希望数字、单位、日期在译文中与原文严格一致。验收：数字/金额/日期一致性规则校验层覆盖全部译文，不一致即回退原文。依据 D-04。阶段：Phase 2。
- **GOV-05 翻译确定性配置**：作为用户，我希望翻译稳定可预期。验收：温度 0、无思维链模型（R1 类禁用）、上下文滑窗 ≤2 句。依据 AI-SPEC §4。阶段：Phase 2。

### 3.2 可溯源

- **GOV-06 逐句溯源落地**：作为用户，我希望每句译文可回溯。验收：JSONL 事件流逐句落盘（原文/译文/置信/时间戳/术语命中/供应商/模型版本）。依据 D-05/D-08。阶段：Phase 2。
- **GOV-07 语句级时间戳**：验收：每句记录相对会话起始的 ms 偏移。依据 D-06。阶段：Phase 2。
- **GOV-08 协议溯源字段**：作为用户，我希望手机上也能看到溯源信息。验收：线协议 subtitle 变体新增 confidence + trace（segmentStartMs/termHits/provider/modelVersion），新增 abstained 事件，向后兼容。依据 D-07。阶段：Phase 2。

### 3.3 可观测

- **GOV-09 分阶段成本计量**：作为用户，我希望知道钱花在哪一阶段。验收：STT 按分钟、翻译按 token、TTS 按字符，逐句计量，桌面设置页成本面板可查。依据 D-13。阶段：Phase 2。
- **GOV-10 埋点复用溯源**：验收：埋点日志复用 JSONL 溯源流聚合上报，不造第二套埋点；字段含用户/任务/模型/耗时/状态/错误码。依据 D-18。阶段：Phase 2 埋结构，Phase 8 上报。
- **GOV-11 管理后台看板**：作为运营，我希望公测前能看到成本看板、错误日志、卡点分析、模型切换开关、配额管理、人工干预入口。依据 D-17/D-19。阶段：Phase 8。

### 3.4 可兜底

- **GOV-12 片段级重试**：作为用户，我希望瞬时网络错误不打断对话。验收：超时/429/5xx 重试 2 次、指数退避 100→200ms、总预算 500ms 内放弃该片段并流下一片段；禁止整句串行重试。依据 D-09。阶段：Phase 2。
- **GOV-13 熔断**：验收：供应商连续 2 次失败熔断 120s，半开探测恢复。依据 D-10。阶段：Phase 2。
- **GOV-14 降级展示**：作为用户，我希望供应商故障时看到明确提示而非静默。验收：红色微章 +「翻译服务暂时不可用」+ 显示原文 + 副标注「正在重试」（文案中文锁定）。依据 D-12。阶段：Phase 2。
- **GOV-15 partial/final 不变量**：作为用户，我希望永远听不到半句话。验收：「spoken English ⊆ committed finals」零违反（仅 final 触发 TTS）。依据 AI-SPEC 关键失败模式。阶段：Phase 2。
- **GOV-16 备用供应商策略**：验收：A/B 实测双路径均达标且预算允许才配备用 key；否则单供应商 + 降级。依据 D-11。阶段：实验后定。

### 3.5 成本可算

- **GOV-17 预算提示**：作为用户，我希望用量接近阈值时收到提示。验收：月度用量阈值提示式（不硬停），与收费模式联动后细化。依据 D-15。阶段：Phase 2 提示 + Phase 8 联动定价。
- **GOV-18 固定路由**：验收：实验期每阶段单一供应商，自动升降级留到数据积累后。依据 D-14。阶段：Phase 2。

### 3.6 反馈闭环（失败案例库 + 回归评测）

- **GOV-19 失败案例库**：作为开发者，我希望每次错误都被记录并归因。验收：案例结构 = 输入 + 错误输出 + 期望输出 + 根因分类（术语缺失/模型幻觉/音频质量/数字漂移/其他）+ 来源（低置信事件/用户反馈/人工抽检）；JSONL 溯源流中低置信、弃权、数字校验失败三类事件自动成为候选；首个案例已入库（0001：SSE 解析截断丢数字）。依据 D-20。阶段：Phase 2 建库，持续积累。
- **GOV-20 回归评测**：作为开发者，我希望修复过的错误永不回归。验收：每次修复与发布前全量案例库回归（正确案例继续通过 + 失败案例转正为回归测试）；CI 集成（三套测试 + 案例库 runner）全绿才可发布。依据 D-20。阶段：Phase 2 机制 + 全阶段执行。

### 3.7 商业化（Phase 8 承接）

- **GOV-21 公测机制**：作为运营，我希望观察每个用户的使用漏斗。验收：免费公测 + 内测码 + 邮箱注册；账号 → 埋点 → 观测顺序建设。依据 D-17。阶段：Phase 8。
- **GOV-22 分钟包月制**：作为用户，我希望价格可预期。验收：月费含分钟数、超出买量；边际成本 ≤ $3.5/面试小时。依据定价讨论。阶段：Phase 8。
