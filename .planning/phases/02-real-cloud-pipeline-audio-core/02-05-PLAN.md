**研究修正（必须折入，逐条对应）：**
1. **构建阻塞（T5.0 的全部理由）**：`webrtc-audio-processing` 的 bundled 构建需要 meson + ninja + pkg-config + clang。环境实测：**meson / ninja / pkg-config 缺失，且本机没有 Homebrew**；clang 与 rust-objcopy 存在，rustc 1.98.0，目标 `x86_64-apple-darwin`。因此 T5.0 是独立任务：先装（pip3 --user 路径可行——slopcheck 已用同一路径安装过），装不上就**显式降级并取得同意**。
2. **AEC crate 无 VAD**：`webrtc-audio-processing` 只提供 AEC3 / NS / AGC / 高通。**不要**在 `audio/aec.rs` 里塞 VAD；VAD 在 02-03 的 `pipeline/vad.rs`（讯飞 eos + Deepgram vad_events + 本地能量）。
3. **rubato 5.0 是 API 重写**：`FftFixedIn` 在 5.0 **不存在**，不要照 4.x 文档写。用 `Fft` + `FixedSync::Both`，每次处理前用 `input_frames_next()` 拿本次应喂入的帧数；缓冲经 `audioadapter` 抽象（`SequentialSliceOfVecs`）。
4. **cpal 0.18 无热插拔通知**：没有设备变更回调。只能**错误驱动**：从流错误回调观察 `ErrorKind::{DeviceNotAvailable, StreamInvalidated, DeviceChanged, DeviceBusy}` 后重建；且当输入输出是同一设备时必须复用同一个 `Device` 对象（否则 macOS 上会因重复打开而失败）。
5. **无 Cargo workspace**：`cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml`，禁止 `--workspace`；CI 亦然。
6. **帧纪律**：webrtc 处理器固定 10ms 帧（48kHz 下 480 样本），帧长不匹配会 panic——把帧长校验做在入口并在错误信息里写明期望与实际。
</context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CoreAudio 设备枚举 → UI/日志 | 设备名是系统提供的不可信字符串（可含任意字符） |
| 采集/播放回调（实时线程）→ 应用 | 回调中的阻塞、分配或 panic 直接导致音频丢失或崩溃 |
| 系统音频状态 → 路由层 | 只读边界：本阶段只枚举，任何系统级修改属 Phase 3 |
| 回采流 → 隐私面 | 回采可能捕获到系统播放音（含他人声音） |
| AEC 参考 ← 播放链 | 参考信号与真实回声错位会让 AEC 失效（退化为自听回环） |
| PyPI/包管理器 → 构建环境 | meson/ninja/pkg-config 是构建期供应链入口 |
